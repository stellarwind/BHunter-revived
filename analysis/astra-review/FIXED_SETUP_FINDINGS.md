# Three additional math matches under the fixed setup

The delivered [matched_math.cpp](matched_math.cpp) reproduces **four complete original routines together, totaling 335 instruction bytes**. Three are new matches. Two clean builds of this saved source passed all comparisons using the same SP3 C++ frontend, math header, and `/TP /O2 /G5 /ML /Gy` settings used for the earlier translation match.

No flag sweep, per-function optimization overrides, assembly, byte emission, or binary patching was used. All four comparisons are raw byte comparisons with **zero relocation masking**. Only trailing COFF alignment padding is excluded.

## What resolved the mismatches

Straightforward expressions, commutative product permutations, and broad uniform temporary types mostly collapsed to a small number of instruction sequences. The useful evidence came from examining the original loads, arithmetic, and store boundaries.

Cross product matched after capturing selected input components in local float temporaries in the required evaluation order. Captures remain within each component, preserving the original sequential-store behavior when output overlaps an input.

The two transforms first matched their initial output rows. Later rows required selected float/double input captures and expression forms to reproduce the original x87 scheduling. These are valid high-level reconstructions that compile to the observed code. They are not evidence that the historical source used these exact temporary names or mixed temporary types.

The direction transform exposed a persistent context dependency: the matching body differs when compiled alone, but matches in both clean builds of the combined file containing the recovered cross and point functions before it. Adding public function prototypes alone did not reproduce that effect. The delivered translation-unit arrangement is therefore part of the verified baseline; the compiler's internal cause is not established.

## Confidence assessment

**There is enough positive evidence to adopt this exact toolchain/configuration and preserved source context as a provisional matching baseline for further reconstruction of this math block.** It now generates the full instructions of cross product and two transforms, in addition to translation, under one configuration. These matches directly demonstrate that the earlier negative probes did not exclude matching.

This does **not** identify a unique historical flag set, establish that the entire game used these options, or prove the original language/source arrangement. Point and direction transforms are related routines, so their evidence is correlated. The reconstructions were deliberately shaped to match the binary; successful code generation is stronger evidence of a useful working baseline than of historical source provenance.

The independently identified VC5 SP3 runtime remains separate supporting evidence. These new math matches strengthen the case for using the available VC5-family compiler setup, but they do not establish that every object in the executable came from that compiler build.

## Bounded non-matches and retained evidence

Local translation at `00401490` (123 bytes) remained unmatched after direct expression and temporary-form checks; the best prefix was 12 bytes. Work on that function stopped when those forms stopped providing useful progress. The earlier normalization non-matches were not reopened in this block. No global restoration plan was created.
