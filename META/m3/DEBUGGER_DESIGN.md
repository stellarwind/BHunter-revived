# M3 bounded source-check debugger diagnostic

This is an opt-in reference experiment, not a source-game implementation or extension of the ten-function math mapper. The Windows loader starts a byte-identical EXE copy from ignored `build/m3/source-probe`. The debugger stops at the first source-check return; it neither creates a playable slice nor verifies graphics/audio/gameplay. There is no computer-use, visual inspection or injected UI input.

Initial hardware-only probes compiled/linked/ran but timed out: the trace shows DR0/DR1/DR7 cleared before reaching the selected instruction. Failed reports are retained as `source-probe-first-attempt.json` and `source-probe-hardware-attempt.json`; they are not successful source checks.

The revised design uses two temporary software execution breakpoints, at the reviewed RegOpenKeyEx call `00473a61` and its owning first source-check return `004723cf`. Exact instruction bytes are checked before instrumentation. Only the first byte becomes CC in the diagnostic child, and it is restored and instruction cache flushed when reached. Source-call execution resumes at the restored instruction. No original file is patched; no branch or success value is replaced. A timeout/error terminates only the child created by this probe.

Baseline uses the original missing HKLM SourceDir state. Positive/negative cases create a fresh flat HKCU `Software/BhunterM3-<uuid>` key with SourceDir pointing at a recovered real file or a privately altered copy. At the single source-registry call, only hKey and lpSubKey stack arguments change to this private key. All subsequent registry reads, file reads and checksum instructions are original. Keys are removed after target exit; original HKLM views and all four immutable reference hashes are verified before/after. The negative fixture differs only in one data byte.

Record raw EAX acceptance and the thread's x87 control word before the registry call and after the source-check return. The PC53 state measured here covers early startup only; it cannot establish driver, render-thread or gameplay numerical state. A correct expected result is not inferred from injected file paths: each must be observed at the actual original return. No game implementation is admitted from this diagnostic.
