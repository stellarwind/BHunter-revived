# BSP numerical investigation

Question: why do raw sections and analytical 6-8-10 controls pass while real derived bounds disagree with a naive Python mathematical control? Positive control: exact center (3,4,0), squared radius 25, radius 5, root radius 10; real root-radius words also inspected. Stop after interpreting the short x87 arithmetic block and comparing the stored-width contract over the supplied assets, or after one 30-minute block; no flag/header/matching sweep.

The first counterexample is BSP\BILLBRD3.BSP node 0. Stored centers agree. Naive full-precision delta squares produce 209.00003051757812; the initial C float-delta expression produces 209.00001525878906. Original 0044b689..0044b6c8 retains double-precision dx/dy/dz, but FST at 0044b6a4 and 0044b6be supplies rounded binary32 dx and dz multiply operands. The exact source expression under PC53 is `(dx * float(dx) + dy * dy) + dz * float(dz)`, then a binary32 squared-radius store. SQRT reloads that stored value. This is different from both uniformly float and uniformly double delta squares.

The original-derived model must therefore replace the naive mathematical fixture, not merely copy current C results. Initial fixture/report and rejected linked result are retained separately. Explicit double arithmetic and real binary32 operand stores express the observed widths without inline asm or compiler flag changes. No original collision function executes in this investigation.

The second counterexample was CARTIT00.BSP node 0: squared-radius bits matched but SQRT used the unrounded x87 value, yielding radius 2.9554834365844727 instead of the required reload result 2.9554836750030518. A volatile-local attempt still let pinned VC5 reuse excess precision. The diagnostic listing includes the midpoint FST/FST/RET sequence returning the unrounded ST0, rather than reloading the stored volatile float.

The accepted adapter uses real `void bh_round_float(float *, double)` in a separate translation unit. That API writes binary32 memory and has no floating return value. With no cross-TU optimization in the pinned build, the caller must reload the observed float before continuing. It expresses the required memory/rounding boundary in ordinary C, with a real definition, link ownership and negative missing-definition control. No compiler flags or historical matched context changed. This is functional support, not original-function recovery or inline assembly.

Stop condition reached: all node-bound/root words across all 505 real assets agree with the independent instruction-derived PC53 model through all three backends. The analytical 6-8-10 control also passes. This validates the stated source contract; no original collision routine was executed and no universal numerical equivalence or byte-match claim is made. Initial failed controls/results remain separate evidence.
